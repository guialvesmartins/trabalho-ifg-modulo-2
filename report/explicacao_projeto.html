Pilar 1 Modelagem de Dados

Coleta, organização e transformação de dados estruturados (metadados) e não estruturados (áudio) em atributos tabulares prontos para análise e ML.

Pilar 2 Aprendizagem de Máquina

Decisão apoiada O engenheiro de manutenção industrial decide: "Devo parar esta bomba para manutenção agora?" — evitando paradas não programadas e manutenções desnecessárias.

O Problema de Negócio

Indústria 4.0 / Manutenção Preditiva: transformar som em decisão de manutenção.

🎯 Domínio

Uma fábrica opera dezenas de bombas industriais 24/7. Quando uma bomba falha sem aviso, a linha para: produção interrompida e reparo emergencial caro. Quando paramos a bomba "por via das dúvidas", perdemos produção à toa.

👷 Tomador de decisão

O engenheiro de manutenção. Ele precisa saber, com antecedência, quais bombas estão se comportando de forma anômala para planejar a parada no momento certo.

❓ Pergunta que o sistema responde

"Esta bomba está operando com anomalia?" — uma classificação binária: normal ou anomalia (contaminação, vazamento, desbalanceamento).

💰 Impacto esperado

• Redução de paradas não programadas
• Redução de manutenções desnecessárias
• Aumento da vida útil dos equipamentos
• Economia em reparos emergenciais

Da Onda Sonora às Features Tabulares

Etapa de processamento e extração de atributos (requisito 4.3): o áudio bruto é transformado em números que um modelo tabular entende — 100% autoral, com librosa.

🎵 MFCC 80 features

40 coeficientes Mel-Frequency Cepstral × (média, desvio). Capturam o "timbre" do som industrial — são as features mais discriminativas do modelo.

📈 Espectrais 12 features

centroid (grave/agudo), bandwidth, rolloff (85% da energia) e 7 bandas de contrast entre picos e vales.

⚡ Energia & ritmo 2 features

zcr_mean (zero-crossing rate) e rms_mean (energia). A energia é intencionalmente não normalizada — ela é um sinal de anomalia.

Rastreabilidade Cada linha da tabela final carrega um file_id (ex.: pump_id_02_anomaly_00000078) que liga o áudio bruto → features → tabelas dbt → predição no predictions.csv. É o elo do requisito 5.3.

Pipeline ELT — Airflow + dbt + Postgres/Snowflake

Toda a solução é orquestrada por um DAG do Apache Airflow (9 tasks) e modelada com dbt (5 modelos, 16 testes) sobre a base analítica.

DAG etl_pipeline — execução sequencial

Scripts em ingestion/, processing/ e ml/ são reutilizados diretamente pelas tasks (PythonOperator) e pelo Makefile.

Cada etapa, em uma frase

1Baixar dadosdownload_dataset.py

Baixa os áudios de bombas reais do Zenodo (~7,9 GB), com retomada se a conexão cair.

2Subir p/ armazenamentoload_raw_to_s3.py

Guarda os .wav no MinIO (dev) ou no Amazon S3 (prod) — só muda uma variável.

3Extrair metadadosprocess_structured.py

Etiqueta cada som: qual bomba, normal ou anomalia (cria o alvo do modelo).

4Som → númerosextract_audio_features.py

Converte cada áudio em 92 features (MFCC, espectrais, energia) com librosa.

5Juntar tudomerge_features.py

Une metadados + features em uma tabela única (4.205 linhas × 103 colunas).

6Carregar no bancoload_to_postgres.py

Salva a tabela no PostgreSQL (prod: Snowflake) para o dbt transformar.

7Transformar (dbt)dbt run

Organiza em camadas: staging → dim/fact → mart ml_features, pronto para o ML.

8Validar qualidadedbt test

Roda 16 testes (file_id único, condition válida…); se falhar, o pipeline para.

9Treinar e avaliarml/evaluate.py

Treina o MLP hard-code × sklearn, compara baselines e gera o relatório final.

Conceitos-chave & Como Reproduzir

Cards didáticos com os conceitos centrais da solução (clique para expandir) e o passo a passo de reprodução.

MFCC — Mel-Frequency Cepstral Coefficients
Transformam o sinal de áudio em um "retrato" do timbre. Passos: janela → FFT → escala mel (resolução perceptual do ouvido) → log (compressão de faixa dinâmica) → DCT (decorrelação). Os 40 coeficientes resultantes resumem a forma espectral. O log torna o modelo robusto a variação de volume (ganho multiplicativo vira deslocamento aditivo).
ELT × ETL
No ETL os dados são transformados antes de carregar; no ELT são carregados crus na base analítica e transformados dentro dela. Este projeto é ELT: o pipeline carrega ml_features_raw no banco e o dbt executa as transformações (staging → dim/fact → mart) via SQL versionado.
dbt — data build tool
Ferramenta de transformação no banco: cada modelo é um .sql versionado, com dependências declaradas (ref()), materialização configurável (view/table) e testes de qualidade. O dbt também gera documentação e a árvore de linhagem dos dados.
MLP e backpropagation
O Multilayer Perceptron é uma rede de camadas totalmente conectadas. No forward pass os dados fluem entrada→saída; na loss (binary cross-entropy) medimos o erro; no backpropagation usamos a regra da cadeia para calcular os gradientes e atualizar pesos via SGD. O projeto implementa tudo com NumPy.
SGD + momento × Adam
SGD com momento: atualiza pesos na direção do gradiente com "inércia" (momento 0,9), lr fixo. Adam: mantém médias exponenciais do gradiente e do quadrado do gradiente, adaptando a taxa por parâmetro. É por isso que o sklearn converge mais rápido (~58 épocas) e a função de custo não-convexa leva a mínimos equivalentes porém ligeiramente diferentes.
StandardScaler e vazamento de dados
Padroniza cada feature para média 0 e desvio 1 (z-score). Crítico para o MLP (inicialização He assume entradas padronizadas). Nunca ajustar no teste: o scaler é treinado apenas no split de treino e depois aplicado no teste, evitando data leakage. O scaler é exportado para a inferência em produção.
Split estratificado
Como o dataset é desbalanceado (~8:1), um split aleatório poderia deixar o teste sem (ou com poucas) anomalias. train_test_split(stratify=y) garante que treino e teste preservem a proporção das classes (750 normal / 91 anomalia no teste).
Baseline de classe majoritária
Modelo "ingênuo" que sempre prevê a classe mais frequente (normal). Serve de piso: qualquer modelo útil precisa superá-lo. No projeto ele acerta 89,18% de accuracy mas recall 0 — prova de que accuracy isolada engana em dados desbalanceados.
Snowflake + external stage
Snowflake é um data warehouse SaaS (colunar). Os CSVs processados ficam no S3 e são carregados via external stage + COPY INTO — o Snowflake lê o S3 sem copiar para dentro do banco primeiro. O dbt com target snowflake executa as transformações direto no warehouse.
CloudFormation / IaC
Infrastructure as Code: a infraestrutura AWS é descrita em um template YAML versionado e provisionada por um comando — reprodutível e auditável. O template do projeto define VPC, sub-redes, S3, EC2, IAM (menor privilégio), SageMaker e CloudWatch.
DAG no Airflow
Directed Acyclic Graph — o "fluxograma" do pipeline: tarefas (nodes) com dependências (arestas) sem ciclos. O Airflow agenda e re-executa o DAG (schedule="@daily"), registra logs, e permite disparo manual (airflow dags trigger etl_pipeline).
Rastreabilidade file_id
Cada áudio gera um file_id determinístico (pump_id_02_anomaly_00000078) que percorre todo o pipeline: parse → features → merge → tabela ml_features_raw → modelos dbt → predictions.csv. É o que permite voltar do erro de uma predição até o áudio bruto original.

Como reproduzir o projeto do zero

# 1. Sobe containers (Postgres, MinIO, Airflow, Metabase)
make up

# 2. Baixa o dataset do Zenodo (7,87 GB, com resume) e sobe para o MinIO/S3
make ingest

# 3. Extrai metadados + features de áudio + merge → ml_features.csv
make process

# 4. Carrega o CSV no PostgreSQL
make load-db

# 5. Roda as transformações dbt e os testes de qualidade
make dbt-run
make dbt-test

# 6. Treina e avalia os modelos (hard-code vs sklearn)
make ml-train

# 7. Roda os testes unitários
make test

Alternativa: disparar tudo pelo Airflow via make pipeline (executa o DAG de 9 tasks). Documentação completa em README.md e FLUXO.md.
