// A solução em uma frase

Um pipeline ELT completo: o áudio de bombas reais (dataset MIMII) é ingerido e armazenado em S3/MinIO, processado em features numéricas, carregado num data warehouse (Postgres, espelho do Snowflake), transformado em camadas pelo dbt, orquestrado pelo Airflow e consumido em 3 dashboards no Metabase.

  • Docker reproduz o ambiente localmente.
  • Troca para produção (AWS + Snowflake) com 4 variáveis de ambiente.
  • Pipeline reproduzível: `make up && make ingest && ...`

3.1 · Manutenção preditiva vs corretiva vs preventiva

// Corretiva

Reage à falha: a máquina quebra e então conserta. Custo máximo (produção parada, reparo urgente, possível dano maior).

// Preventiva

Manutenção por calendário (ex.: a cada 90 dias). Previne falhas, mas muitas vezes para máquinas que não precisavam — custo desnecessário.

// Preditiva (nosso caso)

Monitora condição real (o som!) e prevê a anomalia antes da falha. É o equilíbrio: detecta problema cedo e só para quando precisa.

3.2 · O dataset MIMII Pump

// De onde vêm os dados

  • MIMII = Malfunctioning Industrial Machine Investigation & Inspection.
  • Criado por Hitachi + Toyota Research, publicado no DCASE 2019 (paper arXiv:1909.09347).
  • Licença CC BY-SA 4.0; download no Zenodo (records/3384388).
  • Áudio gravado com array de 8 microfones, 16 kHz, 16 bits.
  • Ruído real de fábrica misturado a 0 dB SNR (sinal e ruído com a mesma energia).

// O que é "0 dB SNR"?

SNR = relação sinal-ruído. 0 dB significa que a energia do ruído é igual à energia do som da máquina — o sinal está "escondido" no ruído.

ℹ

Isso torna o problema realista e difícil: detectar anomalia em áudio que já vem mascarado por ruído de fábrica. É por isso que os 15 falsos negativos existem.

Nota: no dataset real as pastas se chamam id_XX e abnormal; o pipeline normaliza abnormal → anomaly.

3.3 · ELT vs ETL — por que ELT?

// ETL (clássico)

  • Transforma antes de carregar, num servidor de staging separado.
  • Dados prontos entram no DW, mas transformação pesada fora do banco.
  • Menos flexível para reprocessar; precisa de engine extra (ex.: Spark).

// ELT (nosso caso)

  • Carrega o bruto primeiro; a transformação acontece dentro do DW (Postgres/Snowflake).
  • O dbt transforma em SQL, em camadas (staging → dim/fact → mart).
  • Vantagens: reprocessamento fácil, SQL versionado, escalável no Snowflake.
  • O download/extração vira dado bruto no storage; só o que vai ao banco é o que o modelo/BI consome.

Tarefas sequenciais — cada etapa depende da anterior (dados fluem). Agenda @daily, com retries e trava de execução única (max_active_runs=1) para não corromper arquivos.

// Por que orquestrar?

  • Reprodutibilidade: mesmo código, mesma ordem, mesmo resultado.
  • Resiliência: retry automático, log centralizado, UI de monitoramento.
  • Escalonamento: na produção, o Airflow na AWS executa o mesmo DAG.
  • Os scripts são chamados por tarefas Python/Bash com _call(module) — o DAG é só a orquestração do pipeline existente.

// O que é o modelo estrela

Um fato central (medições) rodeado de dimensões (contexto descritivo). Aqui:

  • dim_machines (dimensão): 1 linha por modelo de bomba — totais, anomalias, duração média.

Fácil para BI (joins simples) e otimizado para consultas analíticas.

P1 Por que manutenção preditiva e não corretiva ou preventiva?
negócio

A corretiva só age depois da falha — é o cenário mais caro (produção parada, reparo urgente). A preventiva para a máquina por calendário, muitas vezes desnecessariamente. A preditiva monitora a condição real (no nosso caso, o som) e prevê a anomalia antes da falha: detecta cedo e só para quando precisa — reduz paradas não programadas e manutenções desnecessárias, aumentando a vida útil do equipamento.

P2 Por que usar som (áudio) para detectar anomalia?
domínio

O som é um sensor não invasivo e barato: capta vibração acústica sem parar a máquina nem instalar sensores no rotor. Uma bomba com contaminação, vazamento ou desbalanceamento muda o perfil espectral/timbral — exatamente o que as features de áudio (MFCC, espectrais) capturam. Isso permite monitoramento contínuo 24/7 com um simples microfone.

P3 O que significa "0 dB SNR" e por que é um desafio?
dataset

SNR é a relação sinal/ruído. 0 dB = a energia do ruído é igual à do sinal da máquina: o som da bomba está mascarado pelo ruído da fábrica. É um cenário realista e difícil — por isso existem anomalias sutis que o modelo não detecta (os falsos negativos). Também mostra que o resultado não é "dados fáceis de laboratório".

P4 Quem criou o MIMII e onde está disponível?
dataset

O MIMII (Malfunctioning Industrial Machine Investigation & Inspection) foi criado pela Hitachi com a Toyota Research, publicado no workshop DCASE 2019 (paper arXiv:1909.09347), licença CC BY-SA 4.0, disponível no Zenodo — o arquivo 0_dB_pump.zip (~7,87 GB) é baixado pelo nosso pipeline de ingestão.

P5 O dataset é desbalanceado. O que isso significa para o projeto?
dados

Sim: 3.749 normais vs 456 anomalias (~8:1). Consequências: (1) split estratificado para manter a proporção no teste; (2) accuracy sozinha engana — um modelo que prevê "sempre normal" acerta 89%; (3) o projeto prioriza recall/F1 da classe anomalia, que é a que interessa ao negócio.

P6 Por que usar MinIO e PostgreSQL em desenvolvimento, se em produção é AWS + Snowflake?
arquitetura

Para desenvolver sem custo e sem internet: o MinIO implementa a API do S3 (é um "S3 local") e o PostgreSQL espelha o papel do Snowflake como DW. Como a troca é só de endpoint/configuração (boto3 com endpoint_url, dbt com env_var), tudo testado localmente funciona igual na AWS trocando 4 variáveis.

P7 Diferença entre ETL e ELT. Por que vocês usam ELT?
conceito

No ETL, a transformação acontece antes de carregar, num servidor separado. No ELT, carrega-se o bruto e a transformação acontece dentro do DW (no nosso caso, com SQL do dbt). Usamos ELT porque: o DW (Postgres/Snowflake) é muito mais poderoso para transformações em SQL; o reprocessamento é trivial (re-rodar o dbt); e a lógica de transformação fica versionada e testável.

P8 Qual o papel do Airflow no projeto?
orquestração

É o orquestrador: agenda e executa a DAG elt_pipeline com as 8 tarefas sequenciais — download, upload ao S3, metadados, features, merge, carga no banco, dbt run e ML. Dá retry automático, logs centralizados, UI de monitoramento e garante a ordem correta (cada etapa depende da anterior).

P9 O que o dbt faz e o que são as camadas?
dados

O dbt (data build tool) transforma os dados em SQL dentro do banco, seguindo um modelo estrela em camadas: staging (limpeza, tipagem — views), dimensões (dim_machines: resumo por modelo de bomba), fatos (fact_audio_analysis: 1 linha por áudio) e marts (ml_features: pronta para ML). Roda dbt run e dbt test — os 16 testes garantem qualidade (not_null, unique, accepted_values).

P10 O que é um modelo estrela (star schema)?
modelagem

É um design dimensional com um fato central (medidas, eventos) conectado a dimensões (atributos descritivos). Aqui: fact_audio_analysis (cada gravação com condição + features) e dim_machines (1 linha por modelo de bomba com totais). Vantagens: joins simples, consultas analíticas rápidas e leitura fácil para BI/Metabase.

P11 Como o projeto muda de ambiente (dev → produção)?
infra

Bastam 4 variáveis de ambiente: em .env.local o S3 aponta para o MinIO e o banco é o Postgres; em .env.prod, o S3 aponta para a AWS e o banco é o Snowflake. O boto3 lê endpoint_url e o dbt seleciona o target via env_var() nos profiles. Nenhuma alteração de código é necessária.

P12 Quais são os dashboards do Metabase?
BI

Três: (1) Visão Geral — KPIs (total de amostras, taxa de anomalia, duração média) e distribuição de condições; (2) Análise de Áudio por Modelo — resumo por modelo, MFCC-1 médio, spectral centroid vs condição, top 10 RMS; (3) Resultados do Modelo ML — acurácia, comparação de métricas, matriz de confusão e predições com erro. Os dashboards 1 e 2 têm filtro por modelo de máquina.

P13 O que acontece se o download do dataset for interrompido?
engenharia

O script de download usa HTTP Range: detecta o tamanho local parcial e retoma de onde parou (bytes=local_size-). Se o servidor ignorar o Range (não responder 206), ele recomeça do zero. Também remove dados sintéticos legados (pastas model_id_XX) antes de extrair o dataset real.

P14 Por que o pipeline é considerado "reproduzível"?
engenharia

Porque com Docker e o Makefile qualquer pessoa executa make up (sobe Postgres, MinIO, Airflow, Metabase), make ingest, make process, make load-db, make dbt-run, make dbt-test, make ml-train e obtém os mesmos resultados — mesmo dataset, mesmo split (random_state 42), mesmas métricas.

P15 Por que o Metabase lê de schemas do dbt?
arquitetura

Os cards SQL do Metabase apontam para public_analytics.fact_audio_analysis e public_analytics.dim_machines — os esquemas gerados pelo dbt. Assim o BI consome dados já limpos, testados e padronizados, em vez de tabelas cruas. As tabelas de ML (model_metrics, model_predictions) ficam em public, preenchidas pelo ml/evaluate.py.
