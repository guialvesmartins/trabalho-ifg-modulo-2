3.2 · Lendo a matriz de confusão

// Os 4 quadrantes

Total 841 = 748+2+15+76. 17 erros no total.

// O que cada erro custa

  • 2 falsos positivos → paramos 2 bombas saudáveis para inspeção. Custo baixo (só inspeção).
  • 15 falsos negativos → 15 anomalias passaram despercebidas. Custo alto (risco de falha/parada).
  • Por isso recall (83,5%) importa mais que precisão aqui — o erro caro é o FN.
!

O threshold 0.5 pode ser ajustado: subir reduz FP, descer reduz FN. É a alavanca de calibração em produção.

3.3 · Métricas — cola rápida

No dashboard 3 você só precisa citar: accuracy 97,98%, precision 97,4%, recall 83,5%, F1 0,899. Em uma frase cada: precision = "quando alarmo, acerto"; recall = "pego 83,5% das anomalias reais"; F1 = equilíbrio dos dois. A definição completa e o porquê de a accuracy sozinha enganar (baseline majoritário com recall 0) estão no guia do Daniel, dono do treinamento.

3.4 · Hard-code vs sklearn

// Por que as matrizes quase idênticas?

Hard-code: 747/3/15/76. Sklearn: 748/2/15/76. Ambos usam a mesma arquitetura (64→32), o mesmo split (random_state 42) e as mesmas features.

As pequenas diferenças vêm dos otimizadores (SGD+momento vs Adam) e da inicialização. O fato de os resultados baterem valida que a implementação manual do forward/backprop está correta.

// E o tempo?

Treino: hard-code ~11,3 s vs sklearn ~3,8 s (Adam + código C otimizado ≈ 3x mais rápido).

Predição: ~12 ms vs ~3 ms — ambos tempo real para a aplicação industrial.

P1 O que o Metabase mostra e como foi configurado?
BI

Três dashboards: Visão Geral (KPIs do dataset), Análise de Áudio por Modelo (features) e Resultados do Modelo ML (métricas, matriz de confusão, erros). Eles leem os schemas gerados pelo dbt. A configuração é automática: o script scripts/setup_metabase.py cria a conexão com o Postgres, as perguntas SQL e os dashboards via API REST quando o container sobe.

P2 Por que 3 dashboards e não 1?
BI

Cada um responde a uma pergunta: o 1 é o negócio (quantas amostras, taxa de anomalia); o 2 é a engenharia de dados (como as features se comportam por modelo); o 3 é o resultado do ML (o modelo funciona?). Separar por tema mantém cada tela focada e permite o filtro analítico por modelo nos dashboards 1 e 2.

P3 Como funciona o filtro por modelo no dashboard?
BI

O dashboard tem um parâmetro mapeado para uma template-tag no SQL do card: {{model_id}} com cláusula opcional [[AND model_id = {{model_id}}]]. Quando o usuário escolhe um valor, o Metabase injeta o filtro; quando deixa vazio, a cláusula é ignorada — o card mostra tudo.

P4 Como se lê a matriz 748/2/15/76?
métricas

748 = normais corretas (VN); 2 = falsos positivos (paramos máquina sã); 15 = falsos negativos (anomalias perdidas); 76 = anomalias detectadas (VP). Total 841. O ponto-chave: 2 FP é bom, 15 FN é o problema — o custo de uma anomalia perdida (falha) é muito maior que o de um alarme falso (inspeção).

P5 Por que hard-code e sklearn têm resultados quase iguais?
ML

Porque ambos implementam a mesma arquitetura (64→32 ReLU), treinam com os mesmos dados, o mesmo split estratificado (random_state 42) e as mesmas features escaladas. As pequenas diferenças (1 FP) vêm do otimizador (SGD+momento vs Adam) e da inicialização. Isso valida a implementação manual: se o backprop do hard-code estivesse errado, os resultados divergiriam muito.

P6 Explique precision, recall e F1 em palavras simples.
métricas

Precision: de tudo que o modelo chamou de anomalia, quantas eram mesmo? (97,4%). Recall: de todas as anomalias reais, quantas ele pegou? (83,5%). F1: média harmônica dos dois, um único número que equilibra alarmes falsos e anomalias perdidas (0,899). Para este problema, recall/F1 valem mais que accuracy.

P7 O baseline majoritário tem accuracy alta e recall 0. O que isso ensina?
métricas

Ensina que accuracy em dataset desbalanceado engana. Como 89,2% dos dados são normais, prever "sempre normal" acerta 89,2% — mas nunca detecta uma anomalia (recall 0, precision 0, F1 0). É o piso: qualquer modelo útil precisa superá-lo em recall/F1. Por isso avaliar só accuracy seria um erro grave no nosso contexto.

P8 Como o modelo é carregado na demonstração?
deploy

Com pickle. O ml/evaluate.py salva um Pipeline do sklearn (scaler + MLP juntos) em data/processed/models/mlp_sklearn_pipeline.pkl. Na demo, um pickle.load() traz o modelo pronto; basta aplicar as 96 features de um novo áudio e chamar predict_proba(). O hard-code também é salvo (mlp_hardcode.pkl) e recarregado via HardCodedMLP.load().

P9 O que é o Pipeline salvo no .pkl?
deploy

É um Pipeline do scikit-learn: uma sequência encadeada de StandardScaler + MLPClassifier. Vantagem: o novo dado passa pelo scaler e pela rede num único objeto, sem risco de esquecer a normalização na inferência. É a forma "pronta para produção" de servir o modelo — recebe 96 números e devolve P(anomalia).

P10 Como interpretar P(anomalia) na demo?
interpretação

A saída da sigmoid/softmax é uma probabilidade entre 0 e 1. Com o threshold 0.5: ≥0.5 → anômala; <0.5 → normal. A confiança é tão importante quanto a classe: P=0.999 é anomalia clara (alerta), P≈0.5 é incerto (pede inspeção humana). No nosso teste, anomalias bem detectadas chegaram a P=1.000; os erros tinham P entre 0.000 e 0.401.

P11 O que aparece em "Predições com Erro" no dashboard?
BI

São as amostras do teste em que pred_sklearn != y_true (17 no total). O card lista file_id, modelo, condição real, condição predita e a probabilidade. É o material da análise qualitativa: a maioria é de anomalias sutis com P baixa (0.0-0.4), cujo espectro foge do padrão da própria classe — tipicamente mascaradas pelo ruído de fábrica a 0 dB SNR.

P12 O que acontece se o Postgres não estiver acessível ao rodar a avaliação?
engenharia

Nada quebra. A carga das métricas/predições no Metabase é best-effort: o ml/evaluate.py tenta conectar e, se falhar, imprime um aviso e segue — os CSVs, matrizes e pickles são salvos de qualquer forma. Por isso, para o dashboard ficar atualizado, os containers precisam estar de pé quando o treino roda.

P13 Plano B se a demonstração falhar ao vivo?
apresentação

Três camadas: (1) pré-teste — rodar o notebook inteiro antes, com os mesmos áudios da demo; (2) backups — ter 2-3 áudios alternativos e o screenshot do dashboard do Metabase pronto para mostrar os resultados mesmo sem conexão; (3) discursivo — se falhar na hora, narrar o que o resultado esperado é e mostrar as métricas no dashboard. Nunca deixar o silêncio na tela.
