Roteiro narrado de 3 minutos

0:00~1min
Slide 10

1. Arquitetura 100% AWS

"Para produção, a solução roda inteira na AWS. O fluxo é: os `.wav` brutos ficam no S3; uma EC2 roda o Airflow e os scripts; o Snowflake é o data warehouse; o dbt transforma em camadas e roda os testes; o SageMaker treina o MLP; e o Metabase serve o dashboard. Ou seja, S3 → EC2 → Snowflake → dbt → SageMaker → Metabase: o fluxo completo de dados e decisão na nuvem."

1:00~1min
Slide 11

2. Dev → produção

"O segredo: mesmo código, dois ambientes. Em dev, MinIO e PostgreSQL no Docker; em produção, S3 e Snowflake. A troca é por 4 variáveis de ambiente — o endpoint do S3 aponta para a AWS e o banco vira Snowflake — zero mudanças de código. E usamos infraestrutura como código com um template AWS CloudFormation (S3, EC2, rede e segurança), com o registro de custos documentado — cerca de 40 dólares por mês no cenário acadêmico."

2:00~1min
Slide 12

3. Dashboard e decisão final

"Por fim, o Metabase dá a visão gerencial: KPIs como total de amostras e taxa de anomalia, filtro por modelo de bomba, anomalias por máquina, e a matriz de confusão com as predições que erraram. A regra de decisão é simples: se P(anomalia) > 0,5, o sistema sugere agendar manutenção; senão, a máquina segue operando. O engenheiro recebe o alerta no dashboard e decide com base em dados — áudio, dados, ML e nuvem apoiando a decisão em tempo real. Obrigado!"

3.2 · Como o Snowflake recebe os dados

Os CSVs processados ficam no S3 e o Snowflake lê via external stage + COPY INTO para a tabela ml_features_raw. Depois o dbt materializa as camadas (staging → dim/fact → mart). O Snowflake é SaaS externo — na prática, é o DW de produção; o Postgres é o espelho local para desenvolvimento.

3.3 · Dev → prod com 4 variáveis

// Dev (.env.local)

S3_ENDPOINT=http://minio:9000 · DB_TYPE=postgres → MinIO + Postgres.

// Prod (.env.prod)

S3_ENDPOINT=https://s3.amazonaws.com · DB_TYPE=snowflake → S3 + Snowflake.

ℹ

O boto3 usa endpoint_url e o dbt usa env_var() nos profiles. Troca = configuração, não código.

3.4 · Infraestrutura como código + segurança

// CloudFormation

  • Template YAML (infra/cloudformation.yaml) provisiona S3, EC2, VPC, subnets, security groups, IAM roles.
  • Um comando recria a infraestrutura inteira (aws cloudformation deploy).

// Segurança

  • IAM com menor privilégio: roles separadas para EC2 e SageMaker, só nos buckets do projeto.
  • VPC isolada, SG liberando apenas portas 22 e 8080.
  • Credenciais nunca em código — env vars fora do git + parâmetro NoEcho.

3.5 · O dashboard de decisão

  • KPIs: total de amostras, taxa de anomalia, duração média.
  • Filtro por modelo de máquina (template-tag {{model_id}}).
  • Anomalias por modelo e matriz de confusão com predições que erraram.
  • Regra: P(anomalia) > 0,5 → agendar manutenção; senão → continuar operando.

P1 Qual o papel de cada serviço AWS no fluxo?
cloud

S3 guarda os `.wav` brutos; EC2 roda Airflow + scripts; Snowflake é o DW; dbt transforma em camadas; SageMaker treina o MLP; Metabase serve o dashboard.

P2 O que substitui o quê entre local e AWS?
cloud

MinIO → S3; PostgreSQL → Snowflake; Airflow local → Airflow na EC2; treino local → SageMaker; Metabase local → Metabase na nuvem. O código é o mesmo.

P3 Por que Snowflake e não Redshift?
cloud

O projeto exige Snowflake como tecnologia obrigatória; além disso é SaaS (sem gerenciar infra), escala sob demanda e integra com S3 via external stage. O Redshift aparece como alternativa no CloudFormation acadêmico.

P4 Como o Snowflake recebe os dados?
cloud

Os CSVs processados ficam no S3; o Snowflake lê via external stage + COPY INTO para ml_features_raw. Depois o dbt materializa staging → dim/fact → mart.

P5 Como trocar de dev para produção?
cloud

Com 4 variáveis de ambiente: o endpoint do S3 (MinIO → AWS) e o banco (Postgres → Snowflake). O boto3 usa endpoint_url e o dbt usa env_var() — zero mudanças de código.

P6 O que é CloudFormation / IaC?
infra

Infraestrutura como código: um template YAML descreve a infra (S3, EC2, VPC, IAM, SG) e um comando (aws cloudformation deploy) a cria/reproduz inteira. Versionável e reproduzível.

P7 Qual o papel do SageMaker?
cloud

Serviço de ML da AWS: o notebook treina o MLP (hard-code e sklearn) e exporta os modelos `.pkl`; as métricas voltam para o S3/Snowflake. É o substituto do treino local em produção.

P8 Por que EC2 self-managed e não MWAA?
custo

MWAA (Airflow gerenciado) custa ~350 dólares/mês no mínimo — inviável para escala acadêmica. Uma EC2 rodando o Airflow sai por ~7 dólares/mês no uso parcial. Para esse porte, EC2 é a opção econômica correta.

P9 Quais os custos aproximados da solução?
custo

~20,50 dólares de AWS (EC2, Fargate, S3, EBS, SageMaker, CloudWatch) + ~20 dólares de Snowflake ≈ 40,50 dólares/mês no cenário acadêmico (ligado ~8h/dia útil). Desligar fora do horário reduz bastante.

P10 Como o dashboard apoia a decisão?
negócio

Mostra KPIs, a condição prevista por bomba e a probabilidade de anomalia. Regra: P(anomalia) > 0,5 → agendar manutenção; senão → continuar operando. O engenheiro decide com dados, não por adivinhação.

P11 Como se garante segurança na nuvem?
segurança

IAM com menor privilégio (roles separadas para EC2 e SageMaker); VPC isolada com sub-rede pública/privada; Security Groups liberando só 22 e 8080; credenciais fora do código (env vars + NoEcho).

P12 O que é o filtro por modelo no dashboard?
BI

Um parâmetro do dashboard mapeado para a template-tag {{model_id}} no SQL dos cards. O usuário escolhe um modelo de bomba e todos os cards filtram — cláusula opcional [[AND model_id = {{model_id}}]].
